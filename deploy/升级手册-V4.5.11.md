## 1. 本次修了什么

### 1.1 三张明细表只显示 3~4 行 → 提到「表内一屏能看十几行」

`/insight/milestone` 页面最下方的三张表（**延期项目清单 / 到期提醒 / 在建里程碑计划**）各有 100 多条，
但每张只显示 3~4 行，全靠在表格内部下拉。

**根因**：这三张表开了「首行冻结」，而冻结表头的高度是**按表格在屏幕上的位置动态算**的
（`视口高 − 表格顶部位置 − 24`）。这个测量只在页面**刚打开**时跑一次。三张表位于 6 张图表之后、
页面顶部约 1300px 处 —— 打开那一刻它们还远在屏幕下方，算出来是负数，只能退到「最小 200px」的兜底值，
200px 正好就是表头 + 4 行。

**这已经是第三次踩同一个坑** —— 「成本分析」页的明细表和倚天两个页面早就用固定高度绕开了它，
只有这三张一直没补上。本次除了修好，还加了一条自动检查：**今后谁再加一张冻结表头的表，
测试会直接失败**，逼他明确回答「这张表在页面顶部还是长页面底部」。

### 1.2 ⚠ 一个你需要知道的副作用（笔记本上会看得出来）

修这三张表的同时，把那个「最小 200px」的兜底值抬到了 **440px**（约 10 行）—— 目的是让将来任何一张表
被挤到屏幕下方时，最坏也有 10 行而不是 4 行。

**这个改动在小屏机器上会碰到其它表格**：兜底值的生效条件是 `表格顶部位置 > 视口高 − 464`。

- **1080p 全屏**（浏览器可视高约 950）：其它表格算出 676，大于 440，**兜底值不生效，观感完全不变**
- **1366×768 笔记本**（浏览器可视高实际只有 620~660）：算出约 364，小于 440，**兜底值会生效** ——
  表格会比以前高一些，底边比屏幕底部低约 50px，**最后一行需要滚动页面才看得全**

受影响的是这些页面的主表：在建项目 / 已关闭项目 / 重点项目进展 / 临时重点跟进 / 回款项目 /
回款节点 / 风险跟进 / 回款重点跟进 / 重点商机跟进 / 工时明细。

这是**明知的取舍**：换来的是「表格被挤扁时最坏从 4 行升到 10 行」。如果你的用户主要用 1366×768 笔记本
且觉得这个变化不能接受，改回去只需要把 `frontend/src/composables/useTableMaxHeight.ts` 里的
`DEFAULT_MIN_HEIGHT` 从 440 改回 200 重新构建 —— 三张里程碑表用的是**独立的固定值**，不受这个数影响，
改回去不会让报障复发。

### 1.3 「一次显示多少行」的实际预期（请按这个验收，不要按「15 行」）

三张表现在的高度是**固定 640px**、与页面位置无关，所以能显示几行只取决于每行有多高：

| Tab | 会换行的列 | 实际可见行数 |
|---|---|---|
| **在建里程碑计划** | 无 | **约 15 行** |
| **到期提醒** | 项目名称 | 部分行占两行 → 约 10~14 行 |
| **延期项目清单** | 项目名称、延期节点（**两列**） | 多数行占两行以上 → **约 7~10 行** |

修复前三张都是 3~4 行，所以最差的那张也是 2 倍以上改善。**「延期项目清单」比另两张少是正常的**，
不是没修好 —— 它有两列会自动换行。若你希望它再多几行，可以把 `frontend/src/lib/tableLayout.ts` 里的
`DETAIL_TABLE_MAX_H` 从 640 提高（代价是在小屏笔记本上越过屏幕底部更多）。

## 2. 升级步骤

以下命令假设应用装在 `/opt/pmplatform`、服务名 `pmplatform`，请按实际情况替换。

### 2.1 备份（务必先做）

```bash
cd /opt
sudo tar czf pmplatform-backup-$(date +%Y%m%d-%H%M).tar.gz pmplatform
ls -lh pmplatform-backup-*.tar.gz
```

### 2.2 上传并解压更新包

```bash
cd /tmp
# 把 pmplatform-update-V4.5.11.zip 传到 /tmp
unzip -o pmplatform-update-V4.5.11.zip
ls pmplatform-update-V4.5.11/
```

### 2.3 替换前端产物

```bash
# 前端 dist：先删旧的再拷新的，避免残留旧 hash 文件
sudo rm -rf /opt/pmplatform/frontend/dist
sudo cp -r /tmp/pmplatform-update-V4.5.11/frontend/dist /opt/pmplatform/frontend/

# 后端 .py：本期没有任何改动，拷不拷都行。图省事就一起拷（内容与现网一致）
sudo cp /tmp/pmplatform-update-V4.5.11/*.py /opt/pmplatform/

sudo chown -R pmplatform:pmplatform /opt/pmplatform   # 按实际运行用户替换
```

> **⚠ 不要覆盖服务器上的 `data/`、`input/`、`pmisdata/config.json`。**
> 更新包里**本来就不含**这三样：`data/` 是你的业务数据与账号，`input/` 是数据源，
> `pmisdata/config.json` 存的是超管在页面里贴的 PMIS 会话 cookie——用开发机那份覆盖过去，
> 「下载数据」会立刻失效，而报错长得像「PMIS 登录过期」，很难想到是升级覆盖导致的。

### 2.4 确认

本期**不需要重启**（0 个 `.py` 改动，静态文件每请求读盘）。想重启也可以：

```bash
sudo systemctl restart pmplatform && sudo systemctl status pmplatform --no-pager
```

浏览器**强制刷新**（Ctrl+F5 / Cmd+Shift+R），确认左上角版本号变成 **V4.5.11**。

> 版本号没变 = `dist` 没换成功，或浏览器还在用缓存。先强刷，再检查 `dist` 目录时间戳。

## 4. 本次仍未验证的部分（如实说明）

- **开发机上没有做浏览器目验。** 开发环境的会话是内存态的，无法在不使用账号口令的前提下登录，
  所以 §1.3 那张「实际可见行数」表是**按代码里的列定义静态推算**的（哪几列会换行 → 每行几行高），
  不是实拍出来的。数量级可信（三张表的高度现在是固定 640px，与页面位置无关），但**具体行数以你在
  浏览器里看到的为准** —— 这正是验证清单第 2、3、4 条要做的事。
- **§1.2 那个「1366×768 笔记本上兜底值会生效」的结论也是算出来的**，没有在真机上量过。
  如果你手边有这样一台机器，升级后打开 `/projects` 看一眼表格底边有没有出屏，就能确认。
- 自动化测试是全绿的：前端 251 个测试文件 / 2270 条用例、后端 1413 条，`verify.sh` 全套一次通过。
  但**自动化测试不做真实绘制**，行高这种东西它测不出来 —— 所以才有上面两条。

## 6. 已知问题（本次未修，供知悉）

### L-64：下钻弹窗里的长表格没有任何高度约束

各页图表点进去的下钻弹窗（里程碑下钻、里程碑状态、项目分析下钻、风险下钻）用的对话框**没有设高度上限**，
且这 4 个是**全量渲染**的。点开一个两三百条的下钻，对话框会被撑到几千像素高，滚的是遮罩层而不是表格本身，
表头也留不住。

（另外 2 个下钻弹窗 —— 回款多维分析下钻、数据下钻 —— 各自截断到 200 条，但**界面上没有任何提示**，
用户看不出被截了。）

**为什么本次没修**：方向与本次相反（那是「表太高」，本次是「表太矮」），且要先定一条「弹窗内表格高度」
的统一口径、动 6 个组件。**注意不能直接套用本次的 640** —— 弹窗的可用高度是「视口高 − 对话框的
外边距/标题/底栏」，与页面位置无关，640 在小屏笔记本上加上对话框边框必然溢出。

已记入 `PROGRESS.md` 的 backlog，等你决定优先级。
