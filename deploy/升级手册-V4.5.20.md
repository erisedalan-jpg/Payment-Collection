## 1. ⚠ 升级前必须先读的三件事

### 1.1 前后端字段改名 → 存在一个「必须尽快关闭」的退化窗口

V4.5.20 把项目对象上的**节点已收**从 `payment.actualTotal` 改名为 `payment.nodeActualTotal`。

改名的理由在 §2.3.2，这里只讲运维后果：**旧数据文件里没有这个新字段名**。所以在「换完程序」到「点完更新数据」这段时间里，页面会这样：

| 位置 | 正常（点过更新数据后） | 退化窗口内 |
|---|---|---|
| `/projects` 回款状态「已回清」 | **213** 个项目 | **0** 个（全部错显为「回款中」） |
| 回款达成率 / 各回款页金额 | 47.56% | 47.56%（**不受影响**，它们取流水口径，字段名没变） |
| `/insight`、回款看板、首页 | 正常 | **不受影响** |

拿**生产数据实测**：676 个在建项目里 **213 个（31.5%）**的回款状态会显示错。

**受影响的只有 `/projects` 这一列** —— 全站读 `nodeActualTotal` 的地方只有两处，另一处（`/insight` 的行级字段）算出来后没有任何消费方，屏幕上看不到。别处的「已回款」「流水累计」走的是 `paymentPmis.actualTotal`（流水净额），**那个字段名没改**。

**所以：重启完立刻点「更新数据」，别隔夜。** 点完即恢复，无需再做别的。

> 反过来「先点更新数据、再换前端」并不能绕开 —— 那样是旧前端读新数据，同样一片 0。**两个方向都有窗口，唯一的办法是缩短它**，不要试图规避。

### 1.2 回款达成率会从 47.85% 降到 47.56%

**这不是数据变少了，是之前算法有偏，现在修正了。** 有人会问，先把话讲清楚：

旧算法里，**分子和分母不是同一批项目** —— 「有回款流水、但合同总额为空」的项目，流水计进了分子，分母却给它记 0。生产实测这样的项目有 **6 个（全是售前服务）**，流水合计 **136.68 万**，把全域达成率从 47.5586% 抬高到 47.8464%（**+0.2878pp**）。

这与 2026-08-03 修掉的 `/insight` 那个 107.57% 是**同一个形状**（分子计了、分母没计），只是这次偏差小到没人会怀疑。

**修法**：合同 ≤ 0 的项目，分子分母**一律不计入**。于是页面上「已回款 ÷ 合同额」自己除一下就等于显示的完成率，不会再出现「两个显示值除不出第三个显示值」。

**被排除的 6 个项目不会藏起来** —— 治理页 `/governance` 新增一张表专门列它们（见 §2.3.4）。

### 1.3 升级包必须是 `--base=/pm/` 构建

线上部署在 `/pm` 子路径下。若打包用的 `dist` 不是 `/pm` 构建，**上线即白屏**。

`make_update_zip.py` 会自检并打印结论，出包后再手工复核一次：

```bash
grep -o '/pm/assets[^"]*' frontend/dist/index.html | head -1
```

## 2. 这 5 个版本各自做了什么

### 2.1 V4.5.16 —— 组织架构部门范围改为「自动认表」

**对本部门（交付实施三部）零影响，已实测，可放心。**

起因是另一个部门要本地部署独立实例。原代码把 `config.DEPT_L3 = "交付实施三部"` 写死在两个读表函数里，别的部门的组织架构表会被**整表丢弃**，主域和倚天工时两条链同时静默清零、零报错。

改成判据取自表自身：

- 表里 `新L3组织` 只有**一个**非空取值 → 就按这个值过滤（新部门零配置开箱即用）
- 有**多个**取值（= 误放了跨部门清单）→ 按 `config.DEPT_L3S` 白名单收；一个都匹配不上就 `[WARN]` 告警
- 无该列 / 该列全空 → 不过滤（既有降级路径原样保留）

**本次实测（生产 `input/组织架构.xlsx`）**：85 行，`新L3组织` 全部是「交付实施三部」，唯一值 → 走第一条分支。新旧两条代码路径的输出**逐行对象同一性全等**（85 → 85）。`read_org_names` 收 85 人 / 11 个 L4 组织，`read_org_roster` 收 85 条 —— 与 V4.5.15 完全一致。

### 2.2 V4.5.17 / V4.5.18 / V4.5.19 —— PMIS 下载相关

**这三个版本是为 Windows 单机 exe 做的。Linux 生产的行为一行没变**，但代码要一起上（同一份仓库）。逐条交代：

| 版本 | 做了什么 | 对 Linux 的影响 |
|---|---|---|
| V4.5.17 | 新增 `/api/pmis/cookie/fetch-local`（超管专属），服务端直接向 PMIS 取 Cookie | **新增端点，不改既有行为**。Linux 上原来的取 Cookie 方式照旧可用 |
| V4.5.18 | `pmisdata/config.json` 不存在时自动用默认模板创建 | **空操作** —— 生产这个文件早就有。且代码**只在文件不存在时**套模板，坏 JSON 会抛出去而不是静默覆盖（避免抹掉运维改过的并发数、阶段开关） |
| V4.5.19 | 下载管线按平台分流 | **Linux 分支明确保持原样**：仍然 `subprocess` 跑 `run_pmis_pipeline.sh`，一个字没动。Windows 才走新增的 `.py` 编排 |

> 升级包**刻意不含** `pmisdata/config.json` —— 那里面有服务器自己的凭证与配置，覆盖过去等于拿开发机的配置盖掉生产的。

### 2.3 V4.5.20 —— 系统审查（本次主体）

2026-08-31 对 Linux 主版本做了一次整体审查，目标是**静默错算**与长期可维护性。以下是修掉的东西。

#### 2.3.1 输入文件就绪度三态化（A-1）

原来判断「文件提供了没有」用的是 `bool(rows)` —— **解析结果为空就当成没提供**。V4.5.14 那次生产报障（「上传了却提示未提供」）就是这个根因，当时只修了节假日表一处，这次把同类全部改掉：

- `provided` 一律用 `os.path.isfile()`（**文件在不在**）
- `rows` 表示**读懂了几行**
- 两者分开，告警才能区分「没放文件」与「文件在但格式坏了」—— 否则运维会被指使去重传一个已经在那儿的文件

涉及 `profit.py`（直接成本 / 预算 / 桥接 / 回款流水）与 `milestones.py`。

#### 2.3.2 顺手修掉一个会让「更新数据」整个崩掉的隐患

`profit.py` 读 CSV 原来只试 `utf-8-sig`，而 `except (OSError, csv.Error)` **接不住 `UnicodeDecodeError`**（它是 `ValueError` 的子类）。这个函数在主管线里被直接调用、调用点没有任何 `try/except`。

**后果**：只要 PMIS/Excel 那边导出一份 GBK 编码的 CSV，整个「更新数据」会崩，报错还是 `UnicodeDecodeError` 而不是「文件编码不对」。V4.4.1 真发生过一次（当时是节假日表）。

已改为按 `utf-8-sig → gbk` 顺序回退。

#### 2.3.3 回款分子字段改名 + 拆掉三条未登记的降级例外

**改名**：项目对象上的「节点已收」原本也叫 `actualTotal`，与 `paymentPmis.actualTotal`（**流水净额**，全站唯一合法分子）同名并列。生产实测两者差 **570 万**（46.36% vs 47.56%）—— 任何人写 `Σ 节点那个 ÷ 合同` 都会静默拿到错的，而代码评审**看不出来**：字段名、类型、数量级全都正常。

现已改名为 `payment.nodeActualTotal`。

**拆例外**：`overview.ts` / `paymentBoard.ts` / `paymentPmis.ts` 三处原本写着「没有流水表时退化用节点口径」—— 那是三条从未登记过的口径例外。现在流水表缺失时分子为 0、比率显 0%，**宁可明显坏，不要悄悄错**。

#### 2.3.4 治理页 `/governance` 新增三样东西

| 新增 | 生产实际会显示 |
|---|---|
| 源卡片「收款阶段台账」 | 已提供，1601 行，匹配 1215 条（匹配率 **75.89%**） |
| 告警表「有合同但无收款阶段节点」 | **31 个项目** |
| 告警表「有回款流水但无合同」（§1.2 被排除的那批） | **6 个项目**，流水合计 136.68 万 |

第一张表补的是一个长期盲区：收款阶段导出脚本若漏掉在建项目，其回款节点会**静默缺失**，此前没有任何校验告警。

#### 2.3.5 早拒 401/403 时先读完请求体

会话过期后提交富文本（长 body），后端直接回 401 并关连接，Windows 内核在「接收缓冲区还有未读数据」时会发 RST，浏览器看到的是**连接被重置**而不是干净的 401。已改为先排空请求体（8MB 封顶）再回。

> 说准一点：这个修复**确实**解决了「会话过期 + 大 body → 连接重置」（4 组剂量实验：60KB→0/40、200KB→7/40、1MB→18/40、1MB 排空后→0/40）。但它与 `verify.sh` 里那个偶发 flake 的**因果链未证实** —— 修复前后都复现不出来，只能说「修完连绿 3 次」。

#### 2.3.6 其余（不影响运行）

- `.gitignore` 补 4 条（本地草稿/截图/审查报告此前既未跟踪也未被忽略，在 public 仓前裸露）
- `deploy/nginx-pmplatform.conf` 三处陈旧数字换实测值（**只改注释，指令未动**）：冷加载合计 29.09 MiB → gzip 后 4.14 MiB
- 7 条僵尸 backlog 作废（指向已随 Vue3 重写删除的文件），未完成条目 62 → 55
- 新增视觉验证回路（`visual.sh` + `tools/visual/`）—— **开发工具，不进 `verify.sh`、不影响生产**
- `projectPivot.ts` 删掉一个从 V4.5.15 起就没被用过的死变量，以及它旁边那句**说反了的注释**（声称该变量「用于『已收金额』展示指标」，实际 `InsightGroup` 里根本没有这个字段）。零行为变化

## 3. 升级步骤

### 3.1 备份（必做）

```bash
cd /opt/pmplatform          # 换成你的实际部署目录
tar czf ~/pmplatform-backup-$(date +%Y%m%d-%H%M).tar.gz .
```

确认备份文件非空再往下：

```bash
ls -lh ~/pmplatform-backup-*.tar.gz | tail -1
```

### 3.2 上传并解压

```bash
# 把 pmplatform-update-V4.5.20.zip 传到 /tmp
cd /tmp && unzip -o pmplatform-update-V4.5.20.zip
```

### 3.3 覆盖程序（后端 + 前端一起换）

```bash
cd /tmp/pmplatform-update-V4.5.20
cp -f *.py /opt/pmplatform/
rm -rf /opt/pmplatform/frontend/dist
cp -r frontend/dist /opt/pmplatform/frontend/
```

> 包里的 `pmisdata/` 脚本按需覆盖；**不要**动 `/opt/pmplatform/pmisdata/config.json`（升级包本来就不含它）。

### 3.4 重启

```bash
sudo systemctl restart pmplatform
sudo systemctl status pmplatform --no-pager
```

### 3.5 ⚠ 立刻点「更新数据」

浏览器 **Ctrl+F5** 强刷 → 进「数据管理」`/data` → 点「更新数据」，等 SSE 进度跑完。

**这一步不能省、不能拖**（原因见 §1.1）。跑完之后 §1.1 那张退化表里的数字才会恢复正常。

日志里应能看到新文案：

```
[INFO] 构建项目主域(PMIS 在建 ∩ 组织架构花名册)
```

（V4.5.15 这里写的是「构建项目主域(交付实施三部)」—— 看到新文案，说明 V4.5.16 的改动确实生效了。）

## 5. 回滚

```bash
sudo systemctl stop pmplatform
cd /opt/pmplatform
tar xzf ~/pmplatform-backup-<时间戳>.tar.gz
sudo systemctl start pmplatform
```

上面这条命令是**整体解压**，`data/` 会一并还原成 V4.5.15 格式，回滚后**不需要**再点「更新数据」。

**⚠ 但如果你只还原了 `.py` 和 `dist`**（没还原 `data/`），则**必须再点一次「更新数据」** —— 此时 `data/analysis_data.json` 已是 V4.5.20 格式（字段叫 `nodeActualTotal`），旧程序找的是 `actualTotal`，会出现与 §1.1 **完全对称**的错显：`/projects` 的「已回清」归零。点一次更新数据，旧程序会重新写回旧格式。

> 一句话记：**程序和 `data/` 必须同代**，还原了一个就得让另一个跟上。
