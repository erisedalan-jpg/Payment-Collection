## 1. 本次修了什么

本轮是一次整体系统审查后的批量修复，22 条确认偏离全部修完，另加审查过程中发现的两条。
下面只列**你会看到或需要动手**的部分。

### 1.1 ⚠ 前端主文件一直在以原文下发（性能，需要改 nginx）

后端 `server.py` 走自绘静态分支，对 `.js` 返回的 Content-Type 是 **`text/javascript`**
（CPython `mimetypes` 硬编码表，Python 3.12 实测），而生产 nginx 的 `gzip_types` 里只写了
`application/javascript` —— **类型对不上，2.6MB 的前端主 chunk 从来没被压缩过**。

- 影响：每次冷加载白烧约 **1.64 MiB**（2,757,000 B 原文 vs gzip 后约 1,037,000 B）。
- 为什么一直没被发现：CSS 和 JSON 的类型是对得上的、压缩正常，只有 JS 这一支是坏的。
- 修复：仓库里两个 nginx 模板都已补齐，**但生产机上的配置要你手工同步**（见 §2.5）。

同批还改了缓存策略：带内容哈希的 `/assets/*` 改为 `immutable` 长缓存（原先是 `no-store`，
每次刷新都把整份产物重下一遍），`/data/*.json` 加了 ETag/304 协商缓存。
`index.html` 仍是 `no-cache`，**不会**出现「升级后用户卡在旧版」的问题。

### 1.2 ⚠ `/insight` 的回款完成率会明显变小（口径修正）

`/insight` 此前用的分母是 `customer.合同总额`（售前项目不回退原项目），而 55% 的在建项目是售前、
这个字段为空，分子却照计 —— 实测全域算出 **107.57%**，11 个 L4 桶里有 8 个大于 100%。

已改为与全站主口径一致（Σ流水净额 ÷ Σ合同总额，分母 `paymentPmis.contract`、售前回退原项目）。
**用真实生产数据对拍：修复后 47.85%，与主口径逐位吻合。**

> 升级后 `/insight` 的数字会从 107.57% 掉到 47.85% 左右。**这是修对了，不是修坏了。**
> 同批还修了 `/activity` 的「回款达成率 ±Xpp」（原先用节点口径）。

### 1.3 `/activity` 升级后**首次**点「更新数据」会显示 `-`

`snapshots.py` 的达成率改用主口径后，新增了一个字段。旧快照里没有这个字段，所以升级后第一次
生成快照时，`/activity` 的「回款达成率 ±Xpp」会显示 `-`；**再更新一次就恢复正常**。

这是有意为之——宁可显示「无数据」，也不回退去读旧字段兜底（那会让错误口径悄悄复活）。

### 1.4 权限判定收严（fail-closed）

原先：某账号在某个域「一页都进不去」时，服务端会**回退到默认数据范围**。而建号时默认
`allowedL4` 是 `['*']`，于是这类账号能直接 `curl` 到**未切分的全量数据**。

已改为 fail-closed（该域零可访问页 → 数据范围为空）。

> **已核对生产 24 个账号，本次改动对所有人零影响。** 唯一命中判据的是 `cuishengqiang`
> 在倚天域，但倚天数据接口本来就有页面权限前置闸会先返回 403，走不到这段逻辑。
> 项目域、商机域 0 命中。

### 1.5 卡片/按钮的 hover 效果一直没生效（视觉）

`theme.css` 里一条注释写了 `--dur-*` 紧跟斜杠，那两个字符合起来提前闭合了注释，后半段中文
漏成 CSS 代码，把紧随其后的 `--lift: -2px` 一起吞掉了（浏览器遇到无效声明会跳到下一个分号才恢复）。

- 后果一：`--lift` 从未被定义 → `.u-lift:hover` 和 4 个 `.dv-btn.primary:hover` 的**上浮效果一次没生效过**。
- 后果二：另一处同样的写法在顶层，漏出的文本被当成选择器一路吞到下一个 `{`，把整条
  `.el-button{transition:...}` 吞掉 → **按钮按下是瞬间跳变，没有过渡**。
- 自 2026-06-30（V2.5.2）起躺了一个多月。构建不报错、测试不变红、产物里还「看得见」令牌
  （esbuild 原样保留文本，容错发生在浏览器端），唯一线索是 build 日志里两行 `css-syntax-error` 警告。

升级后这些微交互会**开始生效**——如果你觉得「界面好像和以前不太一样」，是这个原因。
已加守卫测试（`__cssComment.test.ts`，判据是「CSS 注释外不准出现中文」）防复发。

### 1.6 并发时的「更新数据 / 下载数据」提示

后端的「忙」响应状态码从 200 改成 400（与「抢不到立即 400」的设计约定一致）后，前端两个
composable 仍是先判 `res.ok`，会把「别人正在更新」显示成 **「更新失败 (400)」**。已修正分流顺序，
现在正确显示「已有数据更新正在进行，请等其完成后再试（当前：…）」。

### 1.7 打包路径（本次不影响你，但记录）

`make_deploy_zip.py`（**全新安装**整包）的文件清单是硬编码白名单，漏了 27 个根 `.py`
（全部 `lanxin*`、全部 `yitian*`、`audit`、`portal`、`followup_store` 等）——用它出的包
**解压后服务启动即 `ImportError`**。已改为 glob 收全（21 → 48 个），并实证 `server.py` 的
import 闭包 41 个模块零缺失。

**日常升级包（`make_update_zip.py`，也就是你手上这个）一直是用通配符的，不受影响**，历次升级包都是好的。

## 2. 升级步骤

### 2.1 备份（务必先做）

```bash
cd /opt/pmplatform          # 换成你的实际部署目录
tar czf ~/pmplatform-backup-$(date +%Y%m%d-%H%M).tar.gz .
cp /etc/nginx/conf.d/pmplatform.conf ~/nginx-pmplatform.conf.bak   # 路径按实际
```

### 2.2 上传并解压更新包

```bash
# 把 pmplatform-update-V4.5.13.zip 传到 /tmp
cd /tmp && unzip -o pmplatform-update-V4.5.13.zip
```

### 2.3 覆盖后端代码与前端产物

```bash
cd /tmp/pmplatform-update-V4.5.13

# 后端 .py（包里是全部根级 .py，直接整体覆盖）
cp -f *.py /opt/pmplatform/

# 前端 dist：先删旧的再拷新的，避免残留旧 hash 文件
rm -rf /opt/pmplatform/frontend/dist
cp -r frontend/dist /opt/pmplatform/frontend/

# pmisdata 脚本（如果这台机器在用「下载数据」功能）
cp -f pmisdata/*.py pmisdata/*.sh /opt/pmplatform/pmisdata/ 2>/dev/null || true
```

### 2.4 重启后端（本次**必须**）

```bash
sudo systemctl restart pmplatform
sudo systemctl status pmplatform --no-pager    # 确认 active (running)
```

> 与 V4.5.7 那次「只换 dist、不必重启」不同：本次 `server.py` / `auth.py` / `snapshots.py`
> 都改了，不重启则新逻辑完全不生效。

### 2.5 同步 nginx 配置并 reload（本次**必须**，否则 §1.1 的 1.64 MiB 白烧照旧）

编辑生产的 nginx 配置（`/etc/nginx/conf.d/pmplatform.conf` 或 sites-available 下，按实际路径），
把 `gzip_types` 那一行替换成：

```nginx
gzip_types text/javascript application/javascript application/json text/css text/plain
           image/svg+xml application/xml text/xml;
gzip_min_length 1024;
gzip_proxied any;
```

要点：

- **`text/javascript` 必须在第一位/在列**——这是本次修复的核心，后端对 `.js` 返回的就是它。
- `application/javascript` **一并保留**：Linux 上 `mimetypes` 还会读 `/etc/mime.types`，
  不同发行版可能仍映射到旧类型名，两支都写才与来源无关。
- **切勿加 `text/event-stream`**：SSE 进度流被 gzip 缓冲后，「更新数据」的进度条不再实时。
- `gzip_proxied any` 是新加的：客户端请求带 `Via` 头时（内网前置代理场景）nginx 默认会**整个关掉 gzip**。

仓库 `deploy/` 下两个模板已是改好的版本，可直接对照：
`nginx-pmplatform-port80-pm.conf`（你用的 `/pm` 部署）、`nginx-pmplatform.conf`。

```bash
sudo nginx -t && sudo systemctl reload nginx
```

## 3. 验证清单（升级后照着走一遍）

1. **浏览器 Ctrl+F5 强刷**（`index.html` 是 no-cache，但前置 nginx 可能缓存过）。
2. 右下角/关于页版本号显示 **V4.5.13**。
3. **验证 gzip 真的生效了**（本次最重要的一条）：
   ```bash
   curl -s -I -H "Accept-Encoding: gzip" https://你的域名/pm/assets/index-<hash>.js | grep -i "content-encoding\|content-type"
   ```
   期望看到 `content-encoding: gzip`。`<hash>` 从页面源码或 `dist/index.html` 里取。
   **看不到就是 nginx 那步没生效**，回 §2.5 检查。
4. `/insight` 的回款完成率应落在 **47% 左右**，不再是 107%。各 L4 桶不应再有 >100% 的。
5. 点一次「更新数据」，确认 SSE 进度条正常走完（如果进度条不动了，检查 §2.5 有没有误加 `text/event-stream`）。
6. `/activity` 的「回款达成率 ±Xpp」**首次更新后显示 `-` 是正常的**（§1.3），再点一次更新数据即恢复。
7. 各账号登录后能看到的数据范围与升级前一致（§1.4 已核对为零影响，此处是兜底确认）。
8. 鼠标悬停在可点击的卡片上，应有轻微上浮；点按钮应有平滑过渡（§1.5，这是新生效的）。
