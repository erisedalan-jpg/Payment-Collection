## 1. 这两版做了什么

### 1.1 V4.5.8 —— 把「蓝信上的回复回不来」这件事修好了

现网此前的症状是：员工在蓝信里回复了推送消息，**收件箱永远是空的，且界面上看不到任何错误**。

根因有三环，全部已实证（不是推断）：

- **环①：回调地址漏了 `/pm` 部署前缀。** 请求打到了同机部署的**别的系统**上。
  **这不是超管抄错了** —— 配置界面此前把回调地址写死展示成 `http://<主机>/api/lanxin/callback`，本来就没拼部署前缀，超管是一字不差照抄了系统显示给他的东西。地址已由超管在蓝信后台手工改正；本次代码层面把展示逻辑改成按部署前缀自动推导，防止同类问题再发生。
- **环②：公网可达性 / 验签 / 事件订阅** —— 已实证**全部正常**，不是问题所在。
- **环③：蓝信回调的 `timestamp` 是 19 位纳秒，而代码只除了一次。** 于是**每一条回调都被判定为「时间戳超出有效窗口」**而丢弃，入站链路全死，而验签层面毫无异常、界面上也看不到线索。本次已修（循环逐级降到秒），并把生产日志里抓到的四条真实报文钉成了回归用例。

> **上线后要留意**：存证落盘之后还有**解密**与**解析**两道关卡，此前被上面三环挡着**从未真正跑到过**。修完之后它们才第一次有机会执行。若收件箱出现标着 `unparsed`（未解析）的条目，就是卡在这两关之一 —— **这是设计好的降级行为（看不懂就存证 + 标注，绝不静默丢弃），不是新故障**，报文原文在服务器上可查。

### 1.2 V4.5.8 —— 推送卡片内容增强

- **项目卡从「按原因分行」改成「按项目分行」**：每行是「项目名 + 该项目的各项原因（含明细）」，超过 8 个项目额外挤一行「其余 N 个」。
  旧版按原因分行时，同一个项目命中多个原因会在多行重复出现，实测在「单人 49 个项目」这种上界下出现过「标题说 49 个、正文说另有 60 个未列出」的自相矛盾。改完之后这类矛盾结构上不可能再发生。
- **工时卡**同步增强：加「最近日期」与「动作要求」，推送时间挪到卡片顶栏。
- **卡片底部新增「动作要求」一行**，文案按当前实际可用的回流通道自动切换（见 §1.4）。

### 1.3 V4.5.8 —— 新增「未响应清单」（`/data` 页 tab，仅超管）

推送出去 N 小时仍未收到反馈的，列进一张清单供超管检查。**N 由超管在配置里自己设**（「反馈时限」，1~720 小时）。

> **第一天打开时清单会很长**：它是按发送台账算的，历史上所有推送在当时都没有反馈通道，因此都会被列为「未响应」。**这是数据事实，不是缺陷。**

### 1.4 V4.5.9 —— H5 反馈页：员工点卡片就能逐条填反馈

这是本次的主功能。**不依赖回调**，是一条独立的回流通道：

```
员工收到卡片 → 点击整张卡片 → 蓝信内置浏览器打开填报页 → 逐条填写并提交 → 落进收件箱
```

- 链接**逐人签发**，绑定该员工工号，**48 小时有效**。
- 待办清单取自**推送时的快照** —— 员工看到的就是卡片告诉他的那几项。
- **越权保护**：拿自己的链接去提交别人的项目会被拒绝。
- 提交的内容落进**现有收件箱**，带「H5 反馈」标识，超管归入跟进记录时**自动预选它自带的项目号**（文本回复没有这个信息，得人工判断）。
- 链接失效时页面显示「链接已失效，请联系管理员重新推送」，不是白屏也不是报错页。

**配置界面「动作要求」文案会随通道自动切换**：配了 H5 基地址 → 「请点击卡片逐条反馈」；没配但回调可用 → 「请直接回复本消息反馈」；两者都没有 → 不显示动作要求。

### 1.5 V4.5.9 —— 卡片和填报页显示**项目名**而不是项目编号

现网数据里项目名藏在另一个字段，导致卡片明细行此前显示的是 `WSGF-SS-202606189038` 这类编号。本次已修，卡片与 H5 填报页都显示真实项目名。

## 2. 升级步骤（Ubuntu，约 2 分钟）

```bash
# 0) 上传并解压
cd /opt                      # 按实际部署路径调整
unzip -o pmplatform-update-V4.5.9.zip
cd pmplatform-update-V4.5.9

APP=/opt/pmplatform          # 按实际路径调整

# 1) 备份（.py 与 dist 都要备，本次两者都换）
mkdir -p $APP/backup-$(date +%Y%m%d)
cp $APP/*.py            $APP/backup-$(date +%Y%m%d)/
cp -r $APP/frontend/dist $APP/backup-$(date +%Y%m%d)/dist

# 2) 覆盖后端代码（含两个新模块 lanxin_unresponded.py / lanxin_review.py）
cp *.py $APP/

# 3) 原子替换 dist（先落到同一文件系统的临时目录，再一次性 mv，避免半份状态）
rm -rf $APP/frontend/dist.new
cp -r frontend/dist $APP/frontend/dist.new
rm -rf $APP/frontend/dist.old
mv $APP/frontend/dist $APP/frontend/dist.old && mv $APP/frontend/dist.new $APP/frontend/dist
rm -rf $APP/frontend/dist.old

# 4) 重启（本次必须，Python 代码只在进程启动时加载）
systemctl restart pmplatform
systemctl status pmplatform --no-pager | head -5

# 5) 不需要点「更新数据」，不需要改 nginx
#    ⚠ 也【不要】动服务器上的 pmisdata/ 目录，见下方说明

# 6) 浏览器 Ctrl+F5 硬刷 /pm，左上角版本号应为 V4.5.9
```

> **为什么要 Ctrl+F5**：JS/CSS 文件名带内容哈希、会自动换新，但 `index.html` 可能被浏览器或前置 nginx 缓存住，硬刷可确保拿到新的入口文件。

> **⚠ 包里的 `pmisdata/` 本次不要覆盖。**
> 该目录不是开发机专属工具 —— 「下载数据」功能会在服务器上真的执行 `pmisdata/run_pmis_pipeline.sh`，所以打包脚本固定带上它的脚本。但**本次这几个脚本一个字都没改**，覆盖没有意义；而服务器上的 `pmisdata/config.json`（存 PMIS 会话 cookie，是超管在页面里贴进去的）与 `A.xlsx`（售前↔原项目桥接表）**可能比包里的新**。
> V4.5.9 起打包脚本已**不再**把这两个文件放进升级包（只带脚本），所以照 §2 的步骤走不会误伤；这条提示是防手快多敲一行 `cp -r pmisdata $APP/`。

## 3. 升级后必做的配置（**不做这一步，H5 反馈页等于没开**）

### 3.1 填 H5 对外基地址

1. 用**超管账号**登录 → 进 `/data` 页 → 找到「蓝信推送」配置卡 → 「**H5 反馈页**」小节。
2. 点「**填入建议值**」按钮，然后保存。

> **⚠ 请务必点按钮，不要手抄。**
> 建议值是按本系统**实际部署前缀**自动算出来的。本次修的问题①（回复完全回不来）根因就是「页面显示了一个漏 `/pm` 的地址、超管一字不差照抄」—— 同一个坑不要踩第二次。
>
> 留空 = **不发 H5 链接**（卡片仍会推，只是不可点）。所以这一步不做，H5 功能等于没上。

### 3.2 顺带确认「反馈时限」

同一张配置卡里有「反馈时限（小时）」，默认值即可，也可按需改。它同时决定：卡片上「N 小时内未反馈将列入《未响应清单》」那句话里的 N，以及未响应清单的判定阈值 —— **两者同源，不会出现「卡上写 24 小时、清单按别的数算」**。

> **关于 `data/lanxin_config.json`**：本次会给它追加两个键 —— 顶层 `reviewBaseUrl`（就是上面填的地址）与 `credentials.reviewTokenSecret`（H5 链接的签名密钥，**由服务端在第一次预览/推送时自动生成并落盘**，配置界面上没有也不该有这个输入框）。**其余内容一字不动**，AppSecret 与回调双密钥都不会被覆盖。

## 4. 升级后验证清单

### 4.1 必须先过的三条（不过就回滚）

1. **版本号**：左上角显示 **V4.5.9**。
2. **服务起来了**：`systemctl status pmplatform` 显示 `active (running)`，`journalctl -u pmplatform -n 30` 无 traceback。
3. **H5 页面在**（这条最关键，它验证的是 `dist` 换对了）：
   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" http://localhost/pm/review/anything
   ```
   期望 **200**。若是 404 → `dist` 没换成本包里的，回到 §2 第 3 步重做。

### 4.2 本次主功能（开发环境已逐条验过，现网复核即可）

4. **配置界面**：`/data` 页蓝信配置卡里能看到「H5 反馈页」小节与「填入建议值」按钮；点了之后地址栏里出现的地址**带 `/pm`**。
5. **未响应清单**：`/data` 页有「未响应清单」tab（仅超管可见），能打开、能出数（第一天很长是正常的，见 §1.3）。
6. **端到端走一遍**（**最重要，请务必做**）：
   - 用「预览」看一眼卡片内容，确认明细行显示的是**项目名**而不是编号；
   - 真实推送一条给自己或一位配合的同事；
   - 在手机蓝信里**点开那张卡片** → H5 填报页应能打开，顶部显示「你好，某某」与「请在 N 小时内反馈」；
   - 填一条提交 → 应显示「已提交」；
   - 回到 `/data` 页收件箱 → 应看到这条，带「**H5 反馈**」标识；点「归入」时**项目号应已自动预选**。

### 4.3 蓝信文本回复通道（V4.5.8 修的那条，需要人配合）

7. 让同事**直接回复**那条推送消息（不是点卡片），几分钟后看收件箱是否收到。
   - 收到 → 入站链路完全打通。
   - 没收到但配置卡上「已拒绝 N 次回调」的计数**不再增长** → 说明蓝信侧没推过来，查蓝信后台的事件订阅。
   - 出现标 `unparsed`（未解析）的条目 → 卡在解密或解析关，**这是预期内的降级行为**（报文已存证，不会丢），把该条目截图给开发即可定位。

### 4.4 没被拆坏（本次动了后端多个模块，重点回归）

8. 「更新数据」按钮正常（本次不需要点，但要确认没坏）。
9. 各跟进页、项目清单、回款看板正常打开，数据与升级前一致。
10. 账号登录、权限范围与升级前一致（本次**未动**权限模型）。

## 6. 已知未验证项（如实告知，不影响部署决策）

1. **H5 填报页从未在真实浏览器或手机上打开过**。开发侧做的替代验证是：语法检查通过、用沙箱把整段脚本真跑起来覆盖了 15 个场景（含链接失效、无待办、提交成功/失败、网络异常）、逐项核对了移动端的字号与按钮尺寸。**蓝信内置浏览器的兼容性**与**真机视觉效果**没法在开发机上验 —— 所以 §4.2 第 6 条那个端到端要真的做一遍。
2. **蓝信「整张卡片可点击」这个能力本身**在开发机上无法验证（代码是照蓝信文档与一份可参考的实现写的）。若点卡片没反应，H5 链接可以从「预览」里复制出来手动在手机浏览器里打开，功能一样可用 —— 只是少了「点一下就到」这层便利。
3. 解密与解析两道关卡至今**从未跑过**（见 §1.1 与 §4.3 第 7 条）。**H5 通道完全不依赖它们**，只有蓝信文本回复通道依赖。

## 7. 附：这次为什么要重启、上次为什么不用

V4.5.7 是纯前端修复，只换 `dist` 即可 —— 静态文件由服务逐请求读盘、无内存缓存，换掉即刻生效。

本次不同：`server.py` 等后端模块有改动，且新增了两个模块。Python 只在**进程启动时**把代码读进内存，不重启的话跑的还是旧代码，表现会是「前端更新了、点新功能却报 404」这类前后端版本错配 —— 比不升级更难排查。
