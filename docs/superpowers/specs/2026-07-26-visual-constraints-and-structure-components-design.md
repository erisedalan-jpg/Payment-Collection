# 2a 视觉约束修订 + 结构组件化设计（V4.4.9，Z 级）

> 「整体前端优化」四期计划的第三个交付单元。
> 第二期原定「视觉约束整体重写」，经查证改为**针对性修订 + 结构组件化**，理由见 §1。
> 图表 option 预设（原 ③）拆为独立的 2b，本文不含。

## 1. 查证结论：不推翻，因为现有体系执行度接近 100%

用户原话授权「最大可以接受整个约束推翻重新讨论」。动笔前对 14066 行 vue 代码做了全量扫描：

| 违例类型 | 数量 |
|---|---|
| 硬写 hex 颜色 | **0** |
| 散写 z-index | **0** |
| 硬写 px 字号 | 2 |
| 硬写 px 圆角 | 3 |
| 硬写 box-shadow | 2 |

**这套约束没有名存实亡，反而被严格执行。** 推翻重写要重新论证 17 条里那 9~11 条本来就没问题的，成本高且有把已对齐部分搅乱的风险。故改为针对性修订。

### 1.1 一处必须更正的前期判断

grill 阶段我判断「四条约束合谋压低信息密度」（`--fs-base` 默认 18px、禁密度开关、card 1 主 2 辅、单元格 padding），并据此认为它们是 A 类必改项。

**该判断的前提不成立**：`--fs-base` 的三档（小 16 / 中 18 / 大 20）由 `stores/settings.ts` 运行时写入 `<html>`，切换入口 `DisplaySettings.vue` 就挂在侧栏，**用户可自助切换**。切到小档即整体缩放 ×0.889，一屏多出约 12% 的行 —— 密度早就有用户可控的手段。

由此：
- 「不另设密度开关」这条约束**是合理的** —— 三档字号已经是密度开关，再设一套是两种调节手段并存
- 「`--fs-base` 默认 18px」**不改** —— 觉得挤的用户自己切小档即可

**真正的问题是没人知道这个开关存在**（与 `StatusBadge` 同款问题，见 §3.2）。这不是约束缺陷，是可发现性缺陷，本期在升级手册中说明，不改代码。

### 1.2 一个前期统计方法的漏洞

前述「违例只有 7 处」只统计了**硬写值**，漏掉了「令牌用对了但组合不对」这一类。实例：

```css
.gov-h { font-size: var(--fs-3); font-weight: 700; ... }
.yt-h  { font-size: var(--fs-3); font-weight: 600; ... }   ← 同一级,两种字重
```

规范「排版严格层级」明确要求「每级字号·字重·色锁定」。两者都只用令牌、都不算硬写违例，但组合起来违反了层级规范。**真实的不一致比 7 这个数字多。**

## 2. 问题的准确定义：令牌统一，结构未组件化

用户的质疑是「仅修订约束能否让全站同一风格，而非现在的大量拼凑」。答案是**不能**，因为：

> 约束（令牌层）管的是「用什么值」，管不了「谁来拼装」。

证据 —— **「卡片」在 24 个页面里被自己写了 44 遍**，且彼此并不一致：

| 属性 | 实际用了几种 | 规范怎么说 |
|---|---|---|
| 圆角 | **3 种**（`--r-sm` / `--r-md` / `--r-lg`） | 未规定卡片用哪一级 |
| padding | **5 种**（`--sp-2 --sp-3` / `--sp-4` / `--sp-4 --sp-3` / `--sp-3` / `--card-pad`） | 明写「内边距 `--card-pad` 20」 |
| 背景 | 2 种（`--card` / `--card2`） | 未规定 |
| 阴影 | 多数无，个别 `--shadow-1` | 未规定卡片默认带不带 |

**令牌全用对了，组合没有标准。** 这就是「拼凑」的准确形态，也是纯改约束治不好的原因。

## 3. 范围

### 3.1 约束修订（改 `CLAUDE.md`「设计底层规范」+ `theme.css`）

| 类 | 条目 | 改法 |
|---|---|---|
| **B 表述失效** | 「全站不引入第 16 个色号」，实际 21 个 | 改为**按角色分类计数**：结构中性色 4 + 品牌色 3 + 状态语义色 5 + 状态文字色 5 + 图表分类色 8（其中 5 支复用前述）。总数封顶的写法作废 |
| **C 粒度不足** | 2px 微调无令牌（31 处硬写，占间距违例一半） | 新增 `--sp-0: 2px`，定位为「仅限 chip/badge 内边距、描边偏移等亚栅格微调」 |
| | 图标字号无档（`ProjectsView` 的 `10px`、`PortalLaunchpad` 的 `24px`） | 新增 `--fs-icon-sm: 0.625rem` / `--fs-icon-lg: 1.5rem`，**明确不属于六级文字层级**，仅用于图标与 emoji |
| | inset 描边未覆盖 | 规范补一句：「阴影最多两层」约束的是**投影**；`box-shadow: 0 0 0 Npx inset` 作为选中描边不计入，但只准用 `--accent`、宽度只准 2px |
| **D 缺失** | `PageHeader` / `PageTabs` 无规范条目 | 补：页头 = 标题（`--fs-4`/700/`--txt`）+ 右对齐 actions；tab 条位于页头之下、筛选行之上；两者的间距与形态锁定 |
| **E 组合不一致** | 卡内小标题字重 700 vs 600 | 定为 **`--fs-3` / 600**（取多数派 `yt-h`，它被 5 页使用），`gov-h` 改齐 |
| **F 卡片规格** | 无标准，实际 3 种圆角 5 种 padding | **见 §3.3，本期最核心的一条** |

**不改的**：8pt grid 阶梯、六级字号、三档字号及其默认值、card 1 主 2 辅、阴影两级、可访问性护栏、交互五态、动效两档、表格密度、数字排版、字体、z-index 三级、断点。共 13 条原样保留。

### 3.2 结构组件化

| 组件 | 替换处数 | 现状 |
|---|---|---|
| `AppCard`（新建） | 44 | 无组件，24 页各写 |
| `AppEmpty`（新建） | 13 | 无组件。`cv-empty`/`cd-empty`/`gov-empty` 几乎一字不差 |
| `AppPager`（新建） | 11 | 无组件。`cv-pager`/`pn-pager`/`pov-pager` **完全一字不差** |
| `SectionTitle`（新建） | 10 | 无组件，且字重不一致（见 E 类） |
| `StatusBadge`（**推广既有**） | 32 | 组件已存在且设计良好（5 种 tone、全走状态色令牌），**只被 2 个页面使用** |

`StatusBadge` 一条要特别说明：**它不需要重写**。5 种 tone（ok/warn/danger/urgent/mut）覆盖了全部状态语义，`--r-full` 圆角、`--fs-1` 字号都符合规范。32 处自写 badge/tag/chip 里绝大多数可直接换成它。**这是可发现性问题，不是设计问题** —— 与 §1.1 的字号开关同源。

**明确不抽的**：提示条 `banner`/`alert`（24 处）。`gov-banner` 是横向 flex 布局、`gov-alert` 是内容容器，**结构本就不同**，硬抽会得到一个靠 props 分裂成两种形态的组件。YAGNI。

### 3.3 承重设计：先定规格，再抽组件

**顺序不能反。** 若先抽组件、再让它兼容现有的 3 种圆角 × 5 种 padding × 2 种背景，会得到一个 props 爆炸的 `AppCard`，等于把现状的混乱固化成 API，此后再也收不回来。

正确顺序：**约束层先把卡片规格定死为少数几种，组件只实现这几种。**

定为**三种，不设第四种**：

| 变体 | 圆角 | 内边距 | 背景 | 阴影 | 用途 |
|---|---|---|---|---|---|
| `default` | `--r-lg` | `--card-pad` | `--card` | `--shadow-1` | 页面主区块（图表卡、表格卡） |
| `flat` | `--r-md` | `--sp-3` | `--card` | 无 | 嵌套在其他卡内、或密集排列的次级块 |
| `inset` | `--r-sm` | `--sp-2 --sp-3` | `--card2` | 无 | 卡内的小信息块（如 `av-card` 那种指标格） |

`AppCard` 的 API 只有一个 prop：`variant?: 'default' | 'flat' | 'inset'`（默认 `default`）。**不提供** `padding` / `radius` / `shadow` 等逐项覆盖 —— 需要第四种形态时，先改本规范、再加变体，而不是在调用处传参绕过。

**迁移映射**：44 处按其当前圆角归位（`--r-lg`→default、`--r-md`→flat、`--r-sm`→inset）。少数当前 padding 与目标变体不符的，**以变体为准**（这正是本期要消除的不一致），预期会有轻微视觉变化，列入人工目验清单。

## 4. 测试

1. **`AppCard` 三变体**：各断言其圆角/内边距/背景/阴影四项取值（读源码正则，同 `PageHeader` 契约测试的做法）
2. **`AppCard` 不提供逐项覆盖 prop**：断言其 props 只有 `variant` —— 防今后有人加 `padding` prop 把口子重新打开
3. `AppEmpty` / `AppPager` / `SectionTitle` 各一条渲染断言
4. **`SectionTitle` 字重契约**：`--fs-3` / 600，与 E 类决议一致
5. **全局扫描守卫**（追加进 `views/__pageHeader.test.ts`）：
   - views 里不得再出现自写的 `.xx-card` / `.xx-empty` / `.xx-pager` 类定义（迁移完成的反向证明）
   - views 里不得出现 `font-size: var(--fs-3)` 与 `font-weight: 700` 同时出现在同一规则内（E 类回归网）
6. **反向验证必做**：每个新组件临时改坏一项取值，对应契约必须变红。本仓已有多次假绿先例（V4.0.5 `record_sent`、V4.4.4 恒真断言、V4.4.6 `toContain` 碰瓷同页文案）
