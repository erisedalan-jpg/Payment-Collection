## 3. 九个派生字段（口径定义）

全部在 `yitian.build_yitian_data()` 内计算并随 `data/yitian_data.json` 下发。字符串类一律进码表（`_Dim`）压体积。

### 3.1 客户分类 `custClass`

`客户名 ∈ TOP1000.xlsx` 且 `客户级别 == "TOP1000大客户"` → `TOP1000`，否则 `非TOP1000`。
**注**：既有 `entries.top` 布尔与本字段同源，保留不动（向后兼容）。

### 3.2 客户分级（象限）`custQuad`

取 TOP1000 表的象限**原值**（实测取值：`M1 战略核心区` / `M2 现金牛/打猎区` / `M3 潜力培育区` / `M4 待开拓/长尾区`，注意含空格与斜杠）。匹配不上为空。

**判定一律用前缀匹配**（`startswith("M1")` / `startswith("M2")`），不做全串相等 —— 象限值的后半段是描述性文案，随时可能被业务改字。分组展示时取前 2 字符作为分档键。

> **术语统一**：需求文档中「客户分级」与「客户象限」指同一事物，下文一律用**客户象限**。

### 3.3 市场BG `custBg`

取 TOP1000 表的「市场BG」原值，匹配不上为空。

### 3.4 校准后产研侧产品线 `effLine` + 校准状态 `lineSrc`

**触发条件**：`产研侧产品线 ∈ {"其他", 空}` 且 `工时类型 ∈ {项目类, 售前类, 售后类}`。
**词库**：复用合规检查既有的 `yitian_rules.json → checks.product.lineKeywords`（超管可配、改完即时生效）。
**判定**：拿工作成果全文（大小写不敏感）去撞全部产品线的关键词集合 ——

| 命中数 | `effLine` | `lineSrc` |
|---|---|---|
| 恰好 1 条 | 该产品线 | `calibrated`（已校准） |
| ≥ 2 条 | 保持原值（`其他`/空） | `ambiguous`（多义未校准） |
| 0 条 | 保持原值 | `unmatched`（无匹配） |
| 未触发（原值有效） | 原值 | `raw`（原始） |

**只采纳唯一命中**。实测（1439 行 / 10380 h 待校准）：

| 结果 | 行数 | 工时 | 占待校准 |
|---|---|---|---|
| 唯一命中（可靠校准） | 307 | 2208 h | **21.3%** |
| 多义（≥2 条产品线） | 931 | 6946 h | 66.9% |
| 零命中 | 201 | 1226 h | 11.8% |

**为何不做全量校准**：词库为**反方向**设计（已知产品线验内容），只拿一条产品线的词去测，多义无害；反过来猜产品线，86 个关键词里 **19 个被多条产品线共用**（`探针`→NGSOC/威胁感知/网络流量探针，`天擎``软件``终端``U盘``DLP``EDR``杀毒``minio`→一体化终端/新天擎V10，`集群`→一体化终端/威胁感知），多义率 67%。用优先级表强行选一个，等于把 67% 的下游结论建在无业务依据的拍脑袋上，且错了无信号。

**为何不扩词库**：现词库覆盖 21 条产品线、数据里有 81 条。扩到 81 条会让关键词池翻近 4 倍，**多义率只会更高**。且扩词需产研侧业务知识。词库本就超管可配 —— 需求方随时能在规则页加词，校准率自己涨，**不需要改代码**。

**校准率是治理指标**，必须在页面上给出（§5.2、§5.3.2）。

### 3.5 校准后产品大类 `effCat`

`effLine` → `产品分类.xlsx` → 产品大类；`effLine` 为空或查不到 → `未分类`。

### 3.6 校准后是否渠道商可交付 `effChannel`（bool）

`effLine` → `产品分类.xlsx` 的「是否渠道商可交付」== `渠道商可交付产品`。`effLine` 为空 → `false`。

### 3.7 项目管理工时标签 `pmTag`（bool）

两个条件**任一**成立即为真：

- **条件①**：`工时类型 == 项目类` 且 `工作类型三 ∈ {项目管理, 项目验收, 文档编写与汇报}`
  实测：1466 行 / 8516 h（占客户类工时 13.7%）
- **条件②**：`工时类型 != 售后类` 且 工作成果命中**角色槽位**正则
  骨架固定在代码：`(槽位前缀词)[】\]\s:：]{0,4}[^。；\n]{0,12}?(角色词)`
  实测：954 行 / 5362 h；其中条件①未覆盖、仅靠②进来的增量 533 行 / 2826 h

**必须用角色槽位、不能用裸关键词**。需求原文写「工作成果中，担任角色为项目经理」，若实现为 `"项目经理" in 工作成果`，会多吃 51 行 / 290 h，抽查 6 条**全是假阳性**：

```
… 编辑整理巡检报告并输出给项目经理，签字盖章发客户 …
… 需求已同步至产品经理和项目经理，等待行内反馈 …
… 把服务器降配操作的风险点同步给项目经理和客户 …
… 由项目经理拟送说明邮件至行内技术部评估 …
… 整理设备台帐发送个项目经理 …
… 登记设备信息到设备清单表格，反馈给我司项目经理 …
```
这些人恰恰**不是**项目经理。假阳性会让「可转移」被低估，宁窄勿宽。

**兼任保持命中**：`担任角色：项目经理/工程师` 视为项目管理工时（兼任的那部分工作确实带管理属性）。

### 3.8 客户不可归属 `custUnknown`（bool）

`客户字段为空` 或 `客户字段 ∈ 占位词表`。

**实测**：全库唯一占位词为「**受影响的客户**」，478 行 / 2810 h（占客户类工时 4.5%）。按 953 个客户名全量扫描（关键词：受影响/待定/未知/无/内部/多个/若干/其他/专项），其余命中全为误伤（真实的银行/邮政名恰好含这些字）。升级加固 633 行中**客户字段为空者为 0** —— 不是漏填，是填了占位词。

**范围为全域，不限「升级加固」**。占位词跨 11 种工作类型三分布：

| 工作类型三 | 工时 |
|---|---|
| 升级加固 | 1824 h（65%） |
| 安装部署 | 557 h |
| 项目管理 | 141 h |
| 产品故障处理 | 97 h |
| 其余 7 种（策略调整及优化/测试验证/文档编写与汇报/产品巡检/环境调研/值守保障/项目验收） | 合计 191 h |

只盯升级加固会抓 1824 h、**漏 986 h**，而漏掉的与抓到的是同一个填报习惯。

### 3.9 ★ 可转移非原厂支持 `transferable`（五档枚举，非布尔）

判定顺序（**先判不可归属**，其余按短路顺序）：

```
① 客户不可归属(custUnknown)          → "客户不可归属"
② 客户象限 ∈ {M1*, M2*}              → "不可转移：M1/M2 战略客户"
③ 项目管理工时(pmTag)                 → "不可转移：项目管理工时"
④ 非渠道可交付(!effChannel)           → "不可转移：非渠道可交付产品"
⑤ 以上皆否                            → "★ 可转移非原厂"
```

**为何是五档而不是布尔**：`custUnknown` 那 2810 h 客户象限必然为空，按字面「象限 ≠ M1/M2」会被判进「可转移」—— 那是**编出来的结论**。单列一档是唯一诚实的做法，也让需求方看到「想让这个结论更可信，先把这 2810 h 的客户名填对」。

**统计口径**：仅统计 `工时类型 ∈ {项目类, 售前类, 售后类}`（客户类工时），管理类/业务类/假期类不进此判定。

**实测基线**（数据区间 2026-02-02 ~ 2026-07-19，11981 行，客户类工时 62314 h）：

| 分档 | 工时 | 占比 |
|---|---|---|
| 不可转移：M1/M2 战略客户 | 24504 h | 39.3% |
| **★ 可转移非原厂** | **16734 h** | **26.9%** |
| 不可转移：非渠道可交付产品 | 13277 h | 21.3% |
| 不可转移：项目管理工时 | 4988 h | 8.0% |
| 客户不可归属 | 2810 h | 4.5% |

此表是实施期的**对拍基准**：实现完成后按同一区间跑出的分布若与此显著不符，说明某一环口径写歪。

## 4. 可配置项（`data/yitian_rules.json` 扩展）

沿用 `yitian_rules_config.py` 既有结构，新增 `checks.pmTag` 与 `checks.placeholder` 两节。**全部超管可配、即时生效、不进数据管线**（与 §2.1/§2.2 的源表不同，后者需点「更新数据」）。

```jsonc
"pmTag": {
  "enabled": true,
  "workType3": ["项目管理", "项目验收", "文档编写与汇报"],  // 条件①枚举
  "excludeTypes": ["售后类"],                              // 条件②排除的工时类型
  "rolePrefixes": ["担任角色", "【担任角色】", "本人角色", "角色"],
  "roleKeywords": ["项目经理"]
},
"placeholder": {
  "enabled": true,
  "customerWords": ["受影响的客户"]                        // §3.8 占位词表
}
```

**绝不把正则本身暴露给配置界面**。用户不懂正则，填错的表现是「静默命中 0 条」—— 与本仓反复吃亏的静默失效同类，且用户可控正则有 ReDoS 风险。**词表可配、骨架固定**，关键词一律 `re.escape`。这正是本仓既有模式：必填三段检查就是「关键词列表可配 + `yitian_check._keywords_re()` 拼骨架」。

## 5. 页面与分析块

### 5.1 新页 A：`/yitian/customer-product`「客户与产品分析」

挂 `tabGroup: 'yitian-analysis'`（与 compliance/analytics/trend/customer 同组），**侧栏不增项**（V4.4.7 刚把侧栏从 31 收到 24，不再扩）。

六个分析块：

| 块 | 来源 | 内容 |
|---|---|---|
| 1 | B-1 | **客户支持情况**：按 客户分类 × 客户象限 汇总 —— 支持客户数 / 累计工时 / 项目类 / 售前类 / 售后类 |
| 2 | B-2 + **A-5** | **L4 组织支持客户清单**：按客户名聚合，各类型工时投入 + **主要支持产品**（按工时类型分组各取前 3 个 `effCat`） |
| 3 | B-3 | **TOP1000 覆盖度**：按 市场BG × L3-1 × L4 —— 指名客户数 / 实际支持客户数 / **覆盖率** / 累计工时 / 三类型占比 |
| 4 | B-4 | **产品维度热力图（客户维度）**：客户分类分级 × 产品大类 |
| 5 | **A-2** | **产品维度热力图（组织维度）**：L4 组织 × 产品大类，二级下钻 L4 → 客户分类 |
| 6 | **A-4** | **客户 × 产品交叉分析**：按工时降序 |

**每期各写一份实施计划**，本 spec 为三期共同契约。三期不是独立子系统（二、三期都消费一期产出的派生字段），故不拆分 spec；但一期结束前不启动二期的计划编写 —— 二期的分析块设计依赖一期跑出的真实分布（§3.9 基线表在生产数据上是否成立）。

**一期为何要出 KPI 卡**：判定字段本就在一期算完，做 KPI 卡的增量只有一个卡片组件。更重要的是**让口径错误提前一期暴露** —— 这条判定串了三个新条件 + 一次校准 + 一次占位词识别，任何一环写歪总量都会明显偏离 §3.9 的基线表。在只有一个数字时发现口径错，比六个分析块都做完后发现便宜一个数量级。四个就绪度数字必须与 KPI 同屏 —— 21% 的校准率和 4.5% 的不可归属直接决定这个总量有多少水分，**单给结论不给分母，就是本仓刚在 V4.5.3 修过的「标签与数据不符」**。

## 7. 错误处理与降级

### 7.1 清偿既有静默降级债（本期一并做）

**现状**：`projects.read_top1000` → `_read_header_sheet` 找不到含「客户名称」表头的 sheet 就 `return []`，`read_top1000` 于是返回 `{}` —— **全部客户变非 TOP1000、全部象限变空**，而 `preprocess_data.py` / `projects.py` 里**一条 TOP1000 相关的 WARN/ERROR 都没有**（全仓 grep 结果为零）。页面照常打开，数字悄悄归零。

**触发它只需要下次导出改个列名**。这不是假设：本次 grill 中我自己的对比脚本就一头撞了进去 —— 用新工具那份（象限列名为「客户象限」）跑，`quad` 全空，`M1/M2 战略客户` 档从 24504 h **静默变成 0 h，零报错**。

对比同域内的保护级别：`yitian.REQUIRED_COLS` 缺任一列即打 `[ERROR]` 并跳过整个倚天域，注释明写「不能像 `dict.get()` 那样静默返回 None → 全量误判」。TOP1000 没有任何等价保护。这与 L-41（`holidays.csv` 是 GBK → 线上「工作成果」列全空 → 异常被 `try/except` 吞 → 更新数据还显示成功）是同一类事故的不同入口。

**处置**：

| 检查点 | 触发条件 | 行为 |
|---|---|---|
| TOP1000 文件缺失 | `os.path.isfile` 为假 | `[WARN]`，治理指标记 `provided:false` |
| TOP1000 无表头 / 零行 | `read_top1000` 返回 `{}` 但文件存在 | `[WARN] TOP1000.xlsx 存在但解析出 0 行，客户分类/象限将全部为空` |
| 象限列缺失 | 全部 `quad` 为空但行数 > 0 | `[WARN] TOP1000.xlsx 未找到「象限」或「客户象限」列` |
| 市场BG 列缺失 | 全部 `bg` 为空但行数 > 0 | `[WARN]` |
| 产品分类文件缺失 | 同上 | `[WARN]`，`effCat` 全部 `未分类` |
| 产品线覆盖率 | 工时表出现的产品线未被产品分类表覆盖的比例 > 10% | `[WARN] 产品分类表未覆盖 N 个产品线` |

全部计入 `yitian_data.meta.dataReadiness`，由 `/data` 页与 `/yitian` 总览就绪度卡消费。**告警级、不阻断**（TOP1000/产品大类是附加维度，不该让主域失败）。

### 7.2 一般降级

- 花名册无「直接上级工号」列 → 管理干部集合为空，`管理标签`筛选降级为不可用（打 `[WARN]`）。
- 规则配置缺 `pmTag` / `placeholder` 节 → `yitian_rules_config.default_config()` 补默认值（既有 merge 机制）。
- 倚天域整体沿用既有约定：任何异常不得影响 `analysis_data.json`。

## 9. 已知风险与代价

### 9.1 沿用 139 行 TOP1000 清单的代价（已量化）

平台 `input/TOP1000.xlsx` 139 行，新工具那份 726 行（结构一致、级别列同为「TOP1000大客户」，差别纯粹是行数）。**用户明确选择不换表**，以保持与项目主域同源。

代价实测（同一份工时数据，仅换清单）：

| 分档 | 139 行（采用） | 726 行（对照） | 差 |
|---|---|---|---|
| 不可转移：M1/M2 | 24504 h | 28164 h | −3660 h |
| **★ 可转移非原厂** | **16734 h** | **15098 h** | **+1636 h（虚高 10.8%）** |
| 不可转移：非渠道可交付 | 13277 h | 11597 h | +1680 h |
| 不可转移：项目管理工时 | 4988 h | 4644 h | +344 h |
| 客户不可归属 | 2810 h | 2810 h | 0 |

**「可转移」会虚高约 1636 h（相对 +10.8%）** —— 缺的 587 家里有一批 M1/M2 被误判为「非 M1/M2 → 可转移」。

**收敛路径**：生产上按原格式覆盖一份更全的 `TOP1000.xlsx` 后自动收敛，**不需要改代码**。此代价须写进页面脚注或帮助文案，避免使用者把 26.9% 当作精确值。
